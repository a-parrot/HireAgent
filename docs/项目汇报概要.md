# HireAgent 项目汇报概要

> 整理日期：2026-11-16。以当前代码为准，区分新评估主流程、历史兼容流程和待接入能力。

## 一、项目定位

- **目标**：将岗位规则配置、简历筛选、人工复核、面试排期及历史追溯串成完整的招聘辅助流程。
- **核心思路**：大模型理解简历并提取证据，程序执行条件组合、计算分数与业务控制，人工处理需要复核的结果。
- **业务主线**：配置并发布岗位规则 → 导入简历 → 自动评估 → 人工复核或自动准入 → 安排面试 → 查询记录。

## 二、当前系统功能

### 1. 岗位与规则管理

- 新建、编辑、启用、停用和删除岗位。
- 配置岗位职责、任职要求、硬性条件、评分项、推荐线和复核线。
- 硬性条件支持嵌套“全部满足（且）”和“满足任意一项（或）”。
- 规则先保存草稿，再发布为版本；评估绑定发布版本及规则快照，后续修改不改变历史评估依据。

### 2. 简历导入与管理

- 按岗位导入单份或多份 PDF，支持文件校验、SHA-256 去重及岗位关联。
- 本地提取 PDF 正文，保存原件、解析结果和每次解析的独立历史快照。
- 查看解析状态、简历正文、原件与评估记录；支持重新解析、重新评估。删除岗位简历时级联移除该岗位关联评估并清理面试预约和时段；原件、审计日志及其他岗位数据保留。
- 导入接口支持绑定评分规则并启动评估；已解析的简历可复用正文。

### 3. 简历评估与人工复核

- 先筛选硬条件，明确不符合时直接结束本轮评估，跳过评分。
- 满足或信息待核实的简历进入评分证据提取，再由程序计算分数。
- 按岗位阈值展示高分、临界、低分及未评分结果，支持搜索、筛选和历史查询。
- 硬条件和维度评分以表格展示；“或”条件合并为一条，证据以按钮按需打开并高亮上下文。
- 人工可批准面试、暂缓或补充说明；保存审核人、理由、时间和版本，列表展示已复核状态及审核理由。
- 支持清理符合条件的无效评估记录，保留原件及审计历史。

### 4. 面试排期

- 以候选人为中心展示待排期、已排期，支持姓名、文件名和岗位搜索。
- 单人预约或勾选多人连续排期；选择开始时间后默认每人 45 分钟，可调整结束时间和场间间隔。
- 提交前预览每位候选人的具体时间；支持面试官设置、改期和取消。
- 校验同一面试官跨批次时间冲突，不同面试官可并行面试；重复预约受限制。
- 批量预约同事务提交，任一失败则整体回滚；改期、取消写入事件日志。
- 保留高分候选人自动排期入口；已有会议或通知执行记录的预约禁止直接改期、取消。

### 5. 日志与追溯

- 查询解析历史、历史正文快照、评估执行日志和候选人结果。
- 记录节点状态、失败原因、人工审核、排期变更及外部动作状态。
- 支持评估结果导出、失败重试和人工审核中断后的流程恢复。

## 三、技术选型

| 层次 | 技术 | 主要用途 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite | 组件化页面、类型约束、开发与构建 |
| 界面与通信 | Element Plus、Vue Router、Axios | 表格、表单、弹窗、页面路由和接口请求 |
| 后端 | Python 3.12+、FastAPI、Pydantic | 异步接口、请求校验、结构化模型输出校验 |
| 工作流 | LangGraph、MySQL Checkpointer | 节点编排、条件路由、人工中断及状态恢复 |
| 提示词 | LangChain Core、独立 `.prompt` 模板 | 节点提示词组织、输入渲染和版本追踪 |
| 大模型调用 | HTTPX、OpenAI 兼容 Chat Completions 接口 | 模型服务适配、JSON 输出、超时及有限重试 |
| 数据存储 | MySQL 8.4、SQLAlchemy 异步 ORM、aiomysql | 业务数据、事务、连接池及检查点持久化 |
| 数据库迁移 | Alembic、增量 SQL | 表结构初始化和版本升级 |
| 文档解析 | PyMuPDF、本地文件存储 | PDF 文本提取、原件及解析快照保存 |
| 测试与质量 | pytest、HTTPX、SQLite 测试库、Playwright、Ruff | 后端单元与集成测试、浏览器交互验证、代码检查 |
| 部署 | Docker Compose | 提供后端与 MySQL 容器部署配置 |

- **当前本机模型配置**：`LLM_PROVIDER=llama`，通过自部署 llama-server 的 OpenAI 兼容接口调用 `LLM_MODEL_NAME=qwen3.8`。原 DashScope 配置保留，可按环境变量切换；模型不写死在业务节点内。
- **模型职责边界**：模型用于语义理解、硬条件判断及证据匹配；新流程的计分、阈值分流、预约、冲突校验由程序执行。

## 四、总体设计方案

### 1. 前后端分离、后端分层

- 前端负责交互、状态展示、筛选和操作预览。
- API 层负责接口与参数校验，Service 层负责业务规则及事务，Repository/ORM 层负责数据库读写。
- Client 层隔离模型、PDF、数据库以及会议、通知等外部能力。

### 2. 按职责组织智能体与工作流

| 角色 | 职责 |
| --- | --- |
| 招聘编排角色 `recruitment_agent` | 串联解析、评估、人工复核和面试准入，控制主流程分支 |
| 简历评估角色 `resume_evaluation_agent` | 执行硬条件筛选、评分证据提取、计分及历史评估兼容逻辑 |
| 面试角色 `interview_agent` | 自动准入、检查排期条件和组织高分候选人自动排期 |

- 这些角色是代码职责划分；不代表三个长期独立运行的大模型进程。
- PDF 导入、人工操作和预约管理主要由确定性的业务服务执行，不需要每一步都调用模型。

### 3. 规则驱动、证据约束

- 以发布时的规则快照作为本次评估依据，避免评分标准随岗位编辑发生变化。
- 模型返回结构化 JSON，校验规则项 ID、结果完整性及证据引用。
- 原文证据必须能在输入正文中定位；缺失或无效证据不直接认定满足。
- 当前筛选口径：检查完整简历后仍未匹配到硬条件，记为“不满足”，不编造负面证据；原文冲突、含糊或证据校验异常仍需核实。
- 新流程评分项采用“有有效匹配证据得该项满分，否则 0 分”，各项满分合计必须为 100。

### 4. 持久化与可靠性

- MySQL 保存岗位、规则版本、简历、评估批次、候选人、审核、时段、预约、节点记录和事件。
- 原件及解析产物保存在本地存储目录；数据库保存路径、校验值及相关元数据。
- 评估主图使用 MySQL 检查点；导入流程通过任务表和节点进度记录支持恢复。
- 运行锁防止多个后端实例重复恢复同一数据库任务；候选人锁、文件锁和并发信号量控制重复执行。
- 数据库事务保证审核和排期写入一致；版本校验避免使用过期页面覆盖新决定。
- 检查点连接使用健康检查和连接池；失败保留可重试状态及安全的错误诊断信息。

## 五、各工作流结构与节点职责

### 工作流一：PDF 导入与解析

**结构**：`prepare_import → parse_pdf → save_import_result → 结束`

| 节点 | 功能 | 调用大模型 |
| --- | --- | --- |
| `prepare_import` | 校验 PDF 类型、原件路径及 SHA-256 一致性 | 否 |
| `parse_pdf` | 使用 PyMuPDF 提取正文，保存本次解析产物及历史快照 | 否 |
| `save_import_result` | 确认正文产物存在，保证任务可标记为解析完成 | 否 |

- 解析失败可单独重试；导入运行时保存任务状态、错误和节点进度。

### 工作流二：硬条件优先评估——当前新评估主流程

**结构与分支**：

1. `parse_pdf`：等待解析完成，读取或复用简历正文。
2. `screen_hard_conditions → verify_hard_conditions`：初筛后独立重读原文复核硬条件；明确工作年限由程序辅助校验，两次判断冲突且已有有效证据时转待核实。
   - 明确不满足：标记不推荐，结束，不计分。
   - 满足或无法判断：进入证据提取。
3. `extract_scoring_evidence → verify_scoring_evidence`：提取后独立复核完整评分要求及证据。钢结构专项必须有对应领域依据，一般房地产全流程经验不能替代。
4. `calculate_score`：程序计分并分流。
   - 硬条件仍有待核实项：进入人工复核。
   - 硬条件满足且达到推荐线：`auto_approve`，自动准入面试队列。
   - 达到复核线但未到推荐线：`human_review`，等待人工决定。
   - 低于复核线：不推荐，结束。

| 节点 | 功能 | 调用大模型 |
| --- | --- | --- |
| `parse_pdf` | 取得可用正文，避免重复解析相同文件 | 否 |
| `screen_hard_conditions` | 判断叶子条件满足、不满足或无法判断；程序按 all/any 合并整体结论 | 是 |
| `verify_hard_conditions` | 独立复核原文、通用年限与管理职责，防止漏匹配和无依据淘汰 | 是 |
| `extract_scoring_evidence` | 按评分项匹配证据，校验引用；长正文可分块处理并合并结果 | 是 |
| `verify_scoring_evidence` | 重读完整评分限定与原文，纠正漏匹配、泛化匹配及不相关证据 | 是 |
| `calculate_score` | 合并各项匹配结果、计算总分、执行推荐线和复核线分流 | 否 |
| `auto_approve` | 记录自动准入决定，将合格候选人加入面试队列 | 否 |
| `human_review` | 通过 LangGraph interrupt 挂起，待有效人工决定后恢复 | 否 |

### 工作流三：人工复核与恢复

**结构**：等待审核 → 提交决定 → 保存审核记录 → 恢复评估主图 → 更新状态 → 检查面试安排。

- **批准面试**：保存审核人与理由，更新准入状态，排队恢复中断流程。
- **暂缓**：保存审核人与理由，更新暂缓状态，恢复流程以完成本次决定。
- **补充说明**：保存内容及来源，仍保留待审核状态，不自动批准，也不自动触发重新评分。
- **恢复校验**：检查审核版本、候选人状态与恢复指令一致性；失败可查询日志并重试。

### 工作流四：面试排期

面试排期由业务服务和面试角色协作执行，不是另一个独立的 LangGraph 主图。

**人工排期结构**：选择已准入候选人 → 设置时间与面试官 → 预览 → 事务校验 → 创建时段与预约 → 更新排期状态。

| 步骤 / 方法 | 功能 |
| --- | --- |
| `list_interviews` | 汇总候选人、岗位、预约、时间及待排期/已排期计数 |
| `book` | 按选择顺序生成单人或连续多人时段，默认时长由前端填入，可调整 |
| `check_conflict` | 检查同一面试官跨批次的重叠时段 |
| `reschedule` | 校验预约版本，调整时间与面试官，清除旧预览和旧授权，记录变更 |
| `cancel` | 保存审计快照，取消预约并释放对应时段，候选人回到待排期 |

**自动排期结构**：筛选高分且证据完整的已完成结果 → 自动准入 → 按分数优先安排 → 创建预约或进入候补。

- `auto_schedule`：组织高分候选人自动准入与排期；用户提供开始时间时，生成连续的 45 分钟时段。
- `schedule_ready`：在批次评估稳定后，检查是否有已准入候选人，尝试分配现有未来可用时段。
- `schedule`：按规则排序，跳过已预约者和冲突时段；无可用时段者记录候补原因。

### 工作流五：会议与通知动作

**结构**：查看预览 → 编辑并保存版本 → 人工授权 → 创建会议 → 发送通知 → 记录结果；异常时重试或核实。

| 方法 | 功能 |
| --- | --- |
| `preview` / `edit_preview` | 查看、编辑当前预约的会议通知内容；保存新版本清除旧授权 |
| `approve` | 保存批准人、批准时间及授权快照 |
| `execute` | 按授权版本执行会议和通知，使用幂等键并记录状态 |
| `reconcile` | 对运行中或结果不确定的动作查询平台状态，避免盲目重复发送 |

**当前边界**：会议、通知适配器尚未接入真实平台，默认返回未配置；已经具备预览、审批、状态与审计机制，不应汇报为已能真实创建会议或发送通知。

### 历史兼容流程

旧规则快照保留原评估路径，方便历史任务恢复，不代表新流程重复执行这些节点。

| 节点顺序 | 功能 | 调用大模型 |
| --- | --- | --- |
| `parse_pdf` | 读取简历正文 | 否 |
| `analyze_resume` | 提取事实、姓名、证据和缺失信息 | 是 |
| `evaluate_candidate` | 根据事实及规则生成结构化评估 | 是 |
| `route_candidate` | 校验证据、计算汇总并分流 | 否 |
| `review_evaluation` | 对需复核结果进行二次模型校验 | 是 |
| `summarize_result` | 合并二次校验意见，进入人工审核 | 否 |
| `auto_approve` / `human_review` | 自动准入或人工决定后结束 | 否 |

## 六、汇报时重点强调

1. **从“模型给结论”转为“模型找证据、程序算分”**，评分规则清晰、证据可查看。
2. **硬条件优先**，明确不合格者提前结束，避免无意义的后续评分调用。
3. **规则版本、证据、审核及操作日志可追溯**，能够说明评估依据和人工处理过程。
4. **人工复核可中断、可恢复**，将模型不确定性留给业务人员确认。
5. **排期以候选人为中心**，覆盖预约、批量预览、冲突检查、改期和取消。

**当前限制**：仅支持可提取文本的 PDF，扫描件需先 OCR；会议与通知待真实平台接入；当前运行锁设计要求同一业务数据库使用单工作流后端实例。
