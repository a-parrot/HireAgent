## 工作流文件规划

以下为文件职责说明；招聘工作流已实现，具体外部平台适配待选定。

| 计划位置 | 作用 |
| --- | --- |
| `app/main.py` | FastAPI 应用工厂与应用入口；backend/main.py 仅负责调用 Uvicorn 启动同一应用 |
| `app/agents/recruitment_agent/recruitment_graph.py` | 顺序连接节点、条件路由、人工中断 |
| `app/agents/recruitment_agent/recruitment_state.py` | 候选人共享 State |
| `app/services/workflow_service/runtime.py` | MySQL 检查点初始化、连接生命周期与后台恢复 |
| `app/services/resume_service/resumes.py` | 本地 PyMuPDF 全文、解析缓存与历史页文本兼容 |
| `app/agents/resume_evaluation_agent/agent.py` | 简历分析与评分 |
| `app/agents/resume_evaluation_agent/decision.py` | 引用校验、总分与阈值分流 |
| `app/agents/resume_evaluation_agent/agent.py` | 临界或存疑结果的模型复核 |
| `app/agents/interview_agent/agent.py` | 系统面试准入、审计和统一排期 |

提示词计划命名为 `resume_analysis.prompt`、`candidate_evaluation.prompt`、`evaluation_review.prompt`。三个智能体共用一个招聘图，内部准备、调用和整理步骤不额外拆图。

## 职责边界

API 接收请求并调用 services；services 负责规则、批量调度、审核恢复、排序排期和外部动作编排；repositories 负责业务表读写；clients 封装外部连接。节点调用业务服务或客户端并更新 State，避免路由中直接调用模型或操作数据库。

统一排期由 schedule_service 在批次层执行，三个智能体仍按候选人顺序运行。检查点由适配器独立管理，业务仓储不手写检查点表。

与参考项目的区别：将 `respositories` 拼写规范为 `repositories`；不引入知识库检索、向量库或 MinIO；PDF 使用 PyMuPDF 本地提取全文，无解析云服务。保留 uv、MySQL 迁移、Ubuntu Compose 和招聘所需原件存储。API 前缀保持技术方案定义，物理目录变化不改变接口契约。

后端已实现岗位、简历、三智能体工作流、审核、排期、导出及外部动作编排；具体会议/通知平台待选，模型权限及真实 MySQL 验收仍待解决。前端目录保持未开发。详见 docs/prompts/验收记录.md。

新增 app/api/resume_api/workspace_router.py，前端 src/views/resumes/ResumeWorkspaceView.vue 对应 /resumes。前端现已具备岗位、简历、批次、审核、排期及日志页面；此前“前端未开发”属于历史记录。具体外部会议/通知服务、真实模型权限及端到端验收仍不在本轮完成范围。

数据库增加 file_import_tasks、job_resumes，两项迁移为 007/008；现共 14 张业务表。原件按 SHA-256 全局复用，岗位关联按 job_id/file_id 唯一；移除不删除历史评估。PDF 保留原件页码，DOCX 使用 LibreOffice 转换 PDF 后的页码。当前未接入 MinerU/OCR，也不引入向量数据库。


## 本地全文解析（当前实现）

当前导入图为 prepare_import → parse_pdf → save_import_result，只支持新 PDF。PDFClient 使用本地 PyMuPDF 提取文本并合并为全文；ImportRuntime 管理本地任务进度、并发和恢复。新结果保存整份正文和来源索引，不再生成 file_pages 或保存页码；历史页文本仅作兼容读取。

RecruitmentState.pages 作为兼容字段名保留，内容实际为正文来源单元列表。正常简历一次读取整份正文；超长文档按标题/完整段落分组。证据契约新增 block_id 并允许 page_no=null，来源核验按文件+正文标识进行。前端同步为全文预览和证据正文查看，不渲染模型 Markdown 为 HTML，避免把文档指令当作页面代码执行。

## 统一解析评估与按 Agent 组织（2026-11-15）

当前前端使用一次“导入并评估”：绑定已发布岗位规则，后台连续完成 本地全文解析、事实提取、评分和阈值分流。达到推荐阈值且硬条件与证据完整者自动进入面试队列；临界分数或信息不足者才调用复核 Agent，再等待人工确认；明确不达标者结束。没有可用面试时段时进入候补。自动准入在 Review/Event 中明确记录“系统自动分流”，不冒充人工决定。

Agent 代码按职责拆分：resume_evaluation_agent 统一负责 PDF 导入、分析、评分、分流与二次复核；interview_agent 保存面试准入与统一排期。recruitment_agent 仅保留总图、共享 State 和历史导入兼容。技术运行时继续负责检查点、并发、持久化、恢复和人工中断。

导入任务与评估任务共享本地缓存和任务进度，不重复执行同一活动解析。评分请求保留 request_id 幂等；相同内容重复导入不会自动创建另一份已有评估。完成后统一排序排期，不让并发候选人抢时段；重启恢复会补做已完成评估的排期。会议与通知继续使用原有预览和人工授权接口。

无需 SQL 迁移。旧审批记录、页证据和中断工作流保留；旧代码导入路径只作兼容，新实现位于各 Agent 目录。具体模型/会议服务的真实端到端验收不由隔离测试代替。

## 评估后管理工作区

前端 views/reviews/EvaluationManagementView.vue 对应 /evaluations，负责得分分组、筛选及历史查询；CandidateDetailView、ScheduleDetailView 通过可选 ID 属性复用为侧栏，保留独立路由。后端 services/review_service/evaluations.py 只查询已有业务表，按记录快照计算得分区间；api/review_api/evaluation_router.py 处理查询参数。人工决定仍由 review_service 提交，检查点恢复仍由 WorkflowRuntime 执行，排期和外部动作仍由 schedule_service 管理。无需重复实现审批与预约逻辑，也不恢复独立批次管理。

## Agent 目录合并与节点拆分（当前实现）

import_agent 已并入 resume_evaluation_agent，导入图和 ImportState 位于该目录。所有节点实现移到各自 Agent 的 nodes/<节点名>.py，不再集中在 agent.py 或 Runtime 的节点名称分支中；各运行时只负责通用调度、事务、进度、审计和恢复。招聘图节点名称与输入输出未改变，保留既有 MySQL 检查点和历史日志兼容。完整目录与职责见 backend/app/agents/README.md。

当前最终保留三个 Agent：recruitment_agent 负责总编排与人工中断；resume_evaluation_agent 合并原导入/复核职责，负责解析、分析、评分、分流与二次复核；interview_agent 负责面试准入与排期。每个节点继续独立保存于所属 Agent 的 nodes/ 下，原检查点节点名称及日志记录保持兼容。详见 backend/app/agents/README.md。
