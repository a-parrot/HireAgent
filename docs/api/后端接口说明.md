# HireAgent 后端接口与交接

## 登录与角色权限

除 /api/auth/login 和最小健康检查外，招聘接口均要求 Cookie 登录；写请求须携带 X-CSRF-Token（来自 hireagent_csrf Cookie）并通过来源校验。未登录/会话失效返回 401，无权限或 CSRF 不通过返回 403。所有业务 API 响应 no-store。当前为系统级权限，各角色均可查看获准模块中的全部岗位数据。

| 方法与路径 | 行为 |
| --- | --- |
| POST /api/auth/login | username、password；设置 HttpOnly 登录 Cookie，返回用户、角色、权限和 must_change_password |
| GET /api/auth/me | 当前用户和权限；不返回密码哈希或认证令牌 |
| POST /api/auth/logout | 吊销当前会话并清除 Cookie |
| POST /api/auth/change-password | old_password、new_password（1–128 位）；吊销全部会话，需重新登录 |
| GET /api/auth/roles | 仅 users.manage，返回角色 ID、编码和名称 |
| GET /api/auth/users | 仅 users.manage，返回用户清单，不含密码字段 |
| POST /api/auth/users | username（3–64 位字母/数字/_.-）、display_name、role_id、password；新用户强制改密 |
| PATCH /api/auth/users/{id} | 可更新 display_name、role_id、status、password；修改后目标用户会话吊销；重置密码要求改密 |
| POST /api/auth/users/{id}/revoke-sessions | 仅 users.manage，吊销目标用户全部会话 |

首次改密前只开放必要认证接口，不允许进入招聘业务。前端传入的人工操作姓名会被服务端登录身份覆盖。完整接口权限映射位于 app/api/authorization.py；后台请求同样校验，文件下载和历史正文无匿名例外。调试文档默认关闭，快照 openapi.json 仍可本地查阅。


新建评估的 rule_snapshot 增加 evaluation_flow=hard_conditions_first_v1，岗位已发布版本不变。硬条件明确失败的记录 processing_status=completed、recommendation=deferred、total_score=null、dimension_scores=[]，表示筛选完成且跳过评分，不属于技术失败。hard_conditions 每项补充 condition_name、blocking（是否真正导致淘汰）；reason 和 evidence_ids 保留原因及原文引用。通过后 dimension_scores 补充 dimension_name、max_score、matched，score 只取 0 或 max_score；总分由程序求和。GET /api/candidates/{id} 新增 rule_snapshot 供详情页展示配置名称。旧结果字段和历史节点兼容，不自动重算旧评估，不需要 SQL 迁移。

精确请求结构以同目录 openapi.json 和运行时 /docs 为准。ID 响应为十进制字符串，请求路径和表单接受整数文本。错误统一使用 HTTP 状态码与 `detail`；404 不存在，409 版本或预约冲突，422 请求结构错误。模型/外部平台未配置或失败不伪造业务成功。

## 岗位

| 方法与路径 | 请求与行为 |
| --- | --- |
| GET /api/jobs | page、page_size，可选 keyword（名称包含搜索）和 status（active/disabled）；默认返回所有未删除岗位，items 含 latest_published_version，返回 items/total |
| POST /api/jobs | name、responsibilities、requirements、draft_rules；创建草稿 |
| GET /api/jobs/{id} | 草稿及 versions，发布版本包含完整 rule_snapshot |
| PATCH /api/jobs/{id} | 必须携带 draft_version，其他字段按需更新 |
| POST /api/jobs/{id}/publish | draft_version、operator_name；校验发布并推进草稿版本 |
| POST /api/jobs/{id}/disable | 停用，历史结果可查 |
| POST /api/jobs/{id}/enable | 重新启用岗位 |
| DELETE /api/jobs/{id} | 204；软删除并停用，不删除发布版本、批次或候选人 |

规则格式示例位于 backend/app/conf/initial_job.json：hard_conditions 采用 all/any 树，叶子为 id/description/evidence_requirement；dimensions 是任意数量的维度，包含 id/name/max_score/criteria/evidence_requirement；review_threshold、recommend_threshold 定义分流；sort_priority 以 total_score 开始，其后引用有效维度并全部 desc；最终候选人 ID 升序。发布校验叶子和维度 ID 唯一、上限合计 100、阈值合法及受保护属性。已发布版本不可直接修改。草稿允许暂未完善，发布时执行基本规则检查。删除后的岗位查询、编辑和发布返回 404，列表不再展示；以其版本创建新批次也会被拒绝，历史批次仍按原快照运行和查询。

## 简历与批次

| 方法与路径 | 请求与行为 |
| --- | --- |
| GET /api/batches | page/page_size，历史批次列表 |
| GET /api/batches/{id} | 批次快照及 progress、total |
| POST /api/batches/{id}/run | 202，幂等启动；重复返回 already_started=true |
| GET /api/candidates | 必填 batch_id；可选 status/recommendation/page/page_size |
| GET /api/candidates/{id} | 原始事实、条件、评分、证据、缺失风险、复核意见、审核历史、预约和动作 |
| GET /api/files/{id} | 原件 application/pdf；前端可用查看器按页码定位 |
| POST /api/candidates/{id}/retry | 202，仅失败状态允许，从失败节点继续 |

候选人不跨批次合并，文件按哈希复用；每批同文件只导入一次。POST 创建新批次用于显式重评，不把相同上传的所有新批次合并。上传列表中的同一文件不重复产生候选人；格式无效会拒绝本次上传，损坏但具 PDF 头的文件可导入后单独解析失败。文件写入与数据库 COMMIT 不确定时保留可能被引用的原件，不自动清理；需要定期核查未引用文件。

processing_status：pending/running/waiting_review/completed/failed。recommendation：recommended/needs_review/deferred，可为空。批次 evaluation_done 表示没有 pending/running，仍可有待审核或失败者，不代表通知完成。

## 人工审核与恢复

POST /api/candidates/{id}/review：

```json
{
  "operation": "approve",
  "review_version": 0,
  "reason": "已核对相关项目与证据",
  "operator_name": "招聘人员",
  "supplements": [{"description": "补充说明", "source": "人工面谈记录"}]
}
```

operation 为 supplement/approve/defer；补充必须有 description/source，不会自动批准。版本取候选人详情当前 review_version。保存决定后返回审核记录，resume_status=pending 表示恢复已排队，不能把它显示为恢复已完成；刷新候选人详情查看 succeeded/failed。重复决定或过期版本 409，失败恢复可通过候选人 retry 继续，不重复写审核决定。人工决定不覆盖模型分数与证据。

## 日志、导出与状态

- GET /api/batches/{id}/events：after_id 游标及 limit，返回 items/next_cursor。
- GET /api/batches/{id}/export?format=json：包含批次及完整逐人记录，证据保留原文片段与来源标识，旧记录可含页码。
- GET /api/batches/{id}/export?format=csv：UTF-8 BOM、动态维度列、复杂对象 JSON 摘要及公式前缀处理。
- GET /api/health 与 /api/health/ready：存活与数据库连通检查。

CSV 和 JSON 是当前查询时的数据视图，不锁定整批结果。需要归档时，在业务停止变更后导出并与 PDF 原件一并保管。

服务是单进程后台任务运行方式：通过 MySQL 命名锁拒绝第二个后端实例；成功节点输出和 LangGraph 检查点共同支持恢复。排期使用单进程日历锁和数据库事务/唯一约束；不得绕过应用直接修改预约表。跨批次同面试官时间冲突同样检查。

## 恢复与动作核实补充

后端启动会重新计算已启动批次的稳定状态，修复“最后候选人已落库但批次状态未提交”的重启窗口；不会自动批准等待人工的候选人。命名锁释放失败时仍关闭检查点上下文。

平台查询超时继续保持 uncertain，不自动重发。具体平台适配器 query 只有明确确认幂等动作未执行时，才能返回 `{"confirmed_absent":true}`；后端将其标记 failed，仍需显式 retry 才重新执行。查询确认成功时返回真实 external_id 与 status=succeeded。所有动作开始、成功、失败、未配置和待核实事件写入 events。


## 岗位简历工作区

| 方法与路径 | 行为 |
| --- | --- |
| GET /api/resume-workspace/jobs | 所有未删除岗位及 resume_count/parsed_count，包含未导入简历的岗位 |
| GET /api/jobs/{job_id}/resumes | page/page_size、可选 keyword/status；返回当前岗位未移除简历及哈希、解析状态 |
| POST /api/jobs/{job_id}/resumes | multipart files（单个或多个）、可选 sha256s（与 files 一一对应）；返回逐文件 accepted/duplicate/rejected，不因格式错误拒绝其他文件；接收后后台本地 PyMuPDF 解析；可同时请求自动评估 |
| GET /api/jobs/{job_id}/resumes/{resume_id} | 原件 SHA-256 实时校验、整份 Markdown（旧记录兼容逐页文本）、最近导入任务/节点进度及该岗位下的历史评估 |
| DELETE /api/jobs/{job_id}/resumes/{resume_id} | 204，移除岗位关联，保留文件、解析内容和历史评估 |
| POST /api/jobs/{job_id}/resumes/{resume_id}/retry | 202，复用现有活动任务或为失败解析创建新任务；已完成文件也可显式重新解析 |
| GET /api/files/{file_id}/preview | PDF 内联预览；历史转换件保留读取兼容 |

resume_id 是 job_resumes.id，与 file_id/candidate_id 不同；ID 均返回十进制字符串。同内容在同一岗位判重复，在不同岗位可新增关联并复用文件。删除后重新导入可恢复关联。file.parse_status 继续为 pending/running/completed/failed，completed 仅表示解析完成。

文档原件接口仍为 GET /api/files/{file_id}：PDF 内联展示，DOCX 作为附件下载。新导入仅支持 PDF，由本地 PyMuPDF 提取文本，扫描件需预先完成 OCR；不再提供 Word 解析。


## 简历统一评估入口（替代独立批次管理）

POST /api/jobs/{job_id}/evaluate，返回 202。JSON 包含 resume_ids、rule_version_id、request_id（16–64 位字母/数字/下划线/短横线）。服务先检查岗位、规则、岗位简历和原件 SHA，再创建内部执行记录并立即排队评估。以岗位锁及持久化事件绑定 request_id，同请求重试复用执行记录，不重复调度；同请求更换简历或规则返回 409。

GET /api/jobs/{job_id}/resumes 增加 latest_evaluation（id、processing_status、total_score、recommendation、error_message、queued），供统一页面轮询。简历详情的 evaluations 增加得分及时间。失败继续使用 POST /api/candidates/{id}/retry。GET /api/candidates/{id}/export?format=json|csv 仅导出指定候选人，不包含同次执行的其他候选人。

已删除 POST /api/batches 与 POST /api/jobs/{job_id}/resume-batches 上传/创建管理入口；内部批次查询、启动、日志与排期接口仍供兼容和关联使用，前端不再提供批次管理页面。无需删除已有表或历史数据。


## 本地 PDF 全文与证据

- POST /api/jobs/{job_id}/resumes 仅接收 PDF；接收后由 PyMuPDF 本地读取，auto_evaluate=false 时只解析；当前前端提交 true，连同评分一起执行。
- GET /api/jobs/{job_id}/resumes/{resume_id} 新增 markdown；新结果 pages=[]、page_count=null，parser_name=pymupdf-text。历史文件仍可返回 pages。
- GET /api/files/{file_id}/content 返回 file_id、markdown；只读取已完成解析，不会触发上传或新解析。未完成/产物缺失返回 409。
- 新 Evidence 使用 file_id、block_id=document、quote，page_no=null；旧 Evidence 的 page_no 可继续使用。后端验证来源和片段，不生成虚构页码。
- 显式 POST /api/jobs/{job_id}/resumes/{resume_id}/retry 也可重新解析已完成文件；前端确认后在本地重提取正文。失败任务重试不再使用远端 ID。
- 无新增表、列或 Alembic revision；现有 Markdown 路径、任务 JSON 进度与候选人 JSON 证据字段承载新结果。

## 一次导入并评估（2026-11-15）

POST /api/jobs/{job_id}/resumes 增加 multipart 字段 auto_evaluate=true、rule_version_id（当前岗位已发布规则 ID）、request_id（16–64 位字母、数字、下划线、短横线）。缺规则时上传前返回 400。开启后返回原文件接收结果，并在有需要处理的简历时增加 evaluation={batch_id,status,already_started}，表示已排队，不表示模型完成。接口默认 false 兼容仅导入调用；前端默认 true。

同内容重复导入且已有评估时保留该评估；同一 request_id 的请求重试复用执行记录。旧简历需要新规则评估时仍使用 POST /api/jobs/{job_id}/evaluate；该入口现在也接收未解析简历，先解析再评分。技术失败用候选人 retry 从失败节点继续。显式重新解析接口仅更新正文，不静默改写既有评分。

latest_evaluation 增加 schedule_status、waitlist_reason，可直接展示已安排或候补。达标结果的 Review 记录 operation=approve、operator_name=系统自动分流、resume_status=not_required；需要复核者继续使用原人工审批接口，完成后自动尝试排期。会议/通知授权接口未改变。

## 评估管理（得分分组、审核与排期）

新增 GET /api/evaluations。可传 job_id、keyword（姓名/文件名）、bucket（high/middle/low/unscored）、min_score/max_score（闭区间，设相同值查看某个分数）、workflow（waiting_review/approved/scheduled/waitlisted/awaiting_schedule/deferred）、latest_only（默认 true）、page/page_size（上限 200）。最低分大于最高分返回 400。

结果包含 items、total、counts、thresholds。每条记录包含岗位名称、所属评分组和规则快照中的推荐/复核阈值。high 为得分达到推荐线，middle 为复核线至推荐线之间，low 为低于复核线，unscored 为无总分；分组不覆盖业务结论，92 分但信息不足仍可处于待人工审核。counts/thresholds 以岗位、关键词及历史范围统计，不因分组、分数区间或处理状态筛选而清零其他分组。

只列出 completed、waiting_review、failed 的已结束评估；默认每个岗位/原文件只取最近一次已结束记录，新的在途评估不遮蔽已有结果。latest_only=false 查看历史。删除的岗位不列入，停用岗位的历史结果仍可查看。

前端 /evaluations 为评估管理工作区。审核侧栏复用 GET /api/candidates/{id} 与 POST /api/candidates/{id}/review，保持审核版本冲突保护及补充说明来源要求。排期侧栏复用既有时段增删改、统一排序预约、候补与会议/通知预览授权接口；时段范围属于所选评估记录，未恢复完成或未准入的候选人不会被安排。未恢复批次创建/删除管理入口，无新增数据库表或列。

## 独立记录日志与历史正文

GET /api/history/imports 支持 job_id、file_id、keyword（文件名/任务编号）、status（pending/running/completed/failed）、page/page_size。返回每次导入/重新解析任务及 has_snapshot；同一文件重复解析有多条记录，移除岗位关联不删除历史。

GET /api/history/imports/{task_id} 返回节点开始/结束/失败原因、解析器版本、正文快照及校验结果。新正文保存于 parsed/{file_id}/imports/{task_id}/，由 file_import_tasks.node_progress.parse_pdf.artifact 保存路径、原件和正文哈希及字数，不覆盖已完成任务的快照。旧记录没有独立快照时 markdown=null 并给出 artifact_error，不使用当前正文冒充历史；文件缺失或校验失败仍可查看日志。

GET /api/history/evaluations 支持 job_id、keyword、status（pending/running/evaluation_done/failed，其中 failed 表示包含失败候选人）、page/page_size；返回全部历史执行记录和状态数量。逐条事件继续使用 GET /api/batches/{id}/events；节点结果继续由 node_executions 保存。

GET /api/scheduling-records 只列出有已准入且评估完成候选人或已有预约的记录，返回岗位及面试人数/已排期人数。面试排期不再用全部历史批次作为首页；完整历史在独立 /history 页面查看。均复用既有业务表，不新增 SQL 迁移。

## 高分自动排期与无效评估删除

POST /api/evaluations/auto-schedule，JSON 可传 job_id、candidate_ids（省略时检查所有在招岗位的最近已结束记录）。仅处理评估完成、达到绑定快照推荐线、recommendation=recommended、无需人工复核且未删除的记录；不会仅凭分数跳过人工。沿用系统准入审计并按各评估记录的排序规则分配已配置的未来时段，跳过过期时段；缺少可用时段则候补。返回 eligible、scheduled、waitlisted、items，重复调用不重复预约。已有已准入者再次调用会返回当前安排状态。

POST /api/batches/{id}/slots 与 PATCH /api/slots/{id} 保存后自动尝试安排该评估记录下已准入、评估已结束的候选人，因此候补在补充可用时段后自动安排，不必等到四个时段才生效。手动统一排期至少需要一个可用时段，已移除原四时段限制。自动排期不会创建会议或发送通知。

DELETE /api/evaluations/{candidate_id} 删除单条无效记录；POST /api/evaluations/delete 的 JSON 为 candidate_ids 数组，批量删除为一个事务。可删除未准入面试、未预约的已结束或等待人工记录；运行中、已准入或已有预约者返回 409。重复删除幂等。

删除采用软删除：在 events 写入 evaluation_deleted，保留 Candidate、NodeExecution、Review、解析快照、检查点和简历原件。评估管理统计与列表、简历最新评估摘要及运行恢复忽略删除标记；删除最新记录不自动把旧记录冒充最新，历史开关仍可查询其他未删除旧评估。已删除候选人详情继续只读并返回 deleted=true，重试/审核返回 410。历史日志继续保留删除事件。无需表结构或 SQL 迁移。

## 指定起始时间自动生成日程

POST /api/evaluations/auto-schedule 增加 starts_at（带时区的未来时间）、timezone（默认 Asia/Shanghai）、interviewer（可选）。前端默认指定起始时间生成，明确以北京时间输入。例如 starts_at=2026-11-16T09:00:00+08:00。

提供 starts_at 时：按总分降序、同分按绑定规则优先级及候选人 ID 排序，给符合高分准入条件、尚无预约者连续生成 45 分钟时段。已有预约保留；同一面试官跨评估记录的已占时间自动避让，当前评估记录已有时段也不重叠；恰好匹配的空闲时段可复用。所有时段及预约在同一事务中写入，重复提交不会重复生成预约，也不会因更换面试官而改动已有预约。

响应新增 created_slots（新增时段）和 new_reservations（新增预约）；eligible/scheduled/waitlisted 仍返回当前结果。生成动作以 auto_scheduled 事件记录 UTC 起止、面试官、展示时区和 45 分钟时长。未提供 starts_at 时兼容原来的已配置时段模式。过去时间或无效时区在准入操作前拒绝，不更改候选人状态。

已移除每条评估最多四个时段的限制；手动与自动均可管理更多时段，每个仍为 45 分钟。无需数据库迁移，会议/通知授权保持原样。

## 从缓存恢复人工审核

`POST /api/candidates/{candidate_id}/restore-review`，无请求体，成功返回 202：`{"candidate_id":"15","status":"running"}`。仅用于 human_review 交接失败、待审核且 recommendation=needs_review 的未删除记录。解析、分析、评分、分流、复核和汇总节点必须均成功且存在必要输出，否则返回 409，保持原失败状态。已删除返回 410，运行锁失效返回 503。接口复用节点缓存恢复人工中断，不调用模型、不提交审核决定；审计事件为 review_recovery_requested。前端随后刷新状态，只有实际进入 waiting_review 才显示“待人工审核”。普通模型或解析失败继续使用原 retry 接口。


简历工作区 GET /api/jobs/{job_id}/resumes 新增 evaluation_status：running（正在评估）、queued（已启动批次中的等待任务）、pending（未启动）、completed、failed、waiting_review、none。与原解析 status 独立，可组合过滤；按每个岗位/文件最新未隐藏结果判定，筛选后再分页。latest_evaluation 新增 progress={current,total} 或 null，current_node 与 updated_at 继续返回。进度来自现有 node_executions JSON，完成后保存正常节点输出，不新增表。


POST /api/evaluations/auto-schedule 当前支持人工已批准候选人：review_status=approved、已有有效总分、processing_status 为 completed 或 waiting_review 时，不再检查推荐阈值/原 AI 结论/needs_human_review，也无需整个内部评估记录 evaluation_done。未批准结果只有满足原有完整证据、高分与完成状态才能系统自动准入。生成和已有时段模式均支持，现有预约保持不变，未批准且待核实、技术失败、已删除及非当前结果继续跳过。参数和响应字段不变，无 SQL 迁移。
